# 零钱簿 · 阿砚决策点

## D-001 本机数据是默认主数据源

- 日期：2026-08-01
- 决策：未主动开启同步时，账目只保存在当前浏览器 IndexedDB 中；远端不可用不得阻塞记账。
- 原因：个人财务数据首先需要隐私、可控和离线可用。
- 状态：有效。

## D-002 金额统一使用整数分

- 日期：2026-08-01
- 决策：程序与持久化层使用整数“分”，只在输入、展示和 CSV 边界转换“元”。
- 原因：避免二进制浮点带来的金额误差。
- 状态：有效。

## D-003 云同步必须可选且端到端加密

- 日期：2026-08-02
- 决策：Supabase 只承载用户主动启用的同步；事件在浏览器端用平台 Web Crypto 加密，解密密钥不上传。
- 原因：跨设备便利不能改变本机优先和服务端不可读账目的边界。
- 状态：有效；协议、RLS 或配对流程变化时必须补针对性测试。

## D-004 CSV 采用预检后确认

- 日期：2026-08-01
- 决策：CSV 固定表头为 `日期,类型,分类,金额,备注`，导入先报告非法行和重复项，再由用户确认写入；导出带 UTF-8 BOM。
- 原因：财务导入必须可理解、可核对，不能静默丢弃或重复写入。
- 状态：有效。

## D-005 阿砚不评判消费

- 日期：2026-08-02
- 决策：阿砚是精打细算但不评判消费的水墨砚貅账灵；回答基于本机账簿，不冒充专业理财顾问。
- 原因：提供帮助和陪伴，不制造财务焦虑。
- 状态：有效。

## D-006 采用空谷式治理层

- 日期：2026-08-09
- 决策：仓库使用“README 对外入口 + MEMORY 事实/决策/待办 + docs 项目志/质量门禁/变更记录/发布检查”的分层模式。
- 原因：把当前事实、历史沿革、长期决策和未来计划分开，避免旧输出或口头计划被误写成已完成状态。
- 影响：正式交付时同步检查代码、测试、README、MEMORY 与 docs；项目志只记录有证据的里程碑。
- 状态：有效。

## D-007 版本与正式交付同步

- 日期：2026-08-09
- 决策：当前迁入基线沿用 `1.0.0`。以后进入正式交付的变更默认按语义版本升级：修复与文档治理升 patch，新增兼容功能升 minor，破坏性变更升 major。
- 影响：版本变化至少同步 `package.json`、`package-lock.json`、README、`MEMORY/事实.md` 与 `docs/变更记录.md`；形成里程碑时同步项目志。
- 边界：版本升级不等于建立标签、发布或部署，后三者仍需用户明确授权和独立验收。
- 状态：有效。

## D-008 同时间流水冲突必须确定性收敛

- 日期：2026-08-09
- 决策：跨设备收到同一流水的多个版本时，先比较 `updatedAt`；时间相同则按完整流水内容的稳定字典序选定唯一结果。
- 原因：即使两个设备产生相同更新时间，事件到达顺序不同也不能让账簿永久分叉。
- 边界：该规则只解决现有流水更新冲突；未来若为预算、分类或删除操作增加版本字段，应使用同一类确定性规则并提供旧事件兼容路径。
- 状态：有效。

## D-009 Supabase 权限必须显式收窄

- 日期：2026-08-10
- 决策：同步表先同时撤销 `anon` 与 `authenticated` 的默认权限，再只授予成员读取和事件追加所需权限；RLS 成员检查函数放在未暴露的 `private` schema；公开的 `create_sync_room`、`join_sync_room` 只授权 `authenticated`。
- 原因：Supabase 项目默认授权会随平台配置变化，不能把“当前没有 UPDATE/DELETE 策略”当作唯一保护层，也不能只撤销 `PUBLIC` 后假设 `anon` 没有显式函数权限。
- 验证：免费隔离项目中，匿名读取/RPC、直接写房间、跨房间追加、事件更新和删除均被拒绝；成员只能读取所属房间并追加密文事件。
- 状态：有效。
